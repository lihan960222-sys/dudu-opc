# 员工原生项目会话 · 实施与验收计划

> **给实施人员**　按 Superpowers 的 `executing-plans` 执行，或用 `subagent-driven-development` 分项实现和复核。下方保留原验收条件，涉及真实账号或产物的项目以现场结果为准。

**目标**　你在飞书交代一次，员工能像你在 Codex 中打开同一项目那样，读资料、改文件、跑命令、观察结果、调整做法，最后由大嘴交付。

**架构**　Suparagent 管员工、工单、权限和消息；员工用自己的引擎、模型和项目目录执行。工单长期保留，每次派工、实际使用的原生会话和交付凭据都能追溯。二狗走同一入口，额外挂载自己的飞书工具。

**技术与依据**　沿用 Python、SQLAlchemy/Alembic、SQLite、Windows 本地 Codex App Server、飞书网关和 Next.js。现有后端也支持 PostgreSQL，迁移要经过仓库现有 CI。[本次设计与验收约定](../specs/2026-11-26-employee-project-runtime-design.md) · [原有 OPC 需求](../../OPC_REQUIREMENTS_ZH.md)

## 二、每个阶段都要遵守的约定

- **老板原话随工单走。** 当前消息、明确引用、相关附件和大嘴的摘要分别保存；员工能取回与本任务相关的原文。大嘴聊天里其他项目的全部记录不会整包交给员工。引用的材料可作资料，授权只认已验证的老板身份和现有岗位设置。
- **执行能力以实际可调用为准。** 同一项目、同一模型、推理强度、账号、已安装工具和授权才适合做桌面对照。不同厂商验证“同一件事能否完成”；不要求输出措辞或耗时相同。依赖桌面宿主的连接单独验证，算作岗位必需的工具必须有等价可用的后台入口。
- **独立的目录权和飞书权。** 自己的项目按档案配置执行，最高档允许自由读写修改；其他员工目录默认不可访问，获得跨岗权限时为只读。已有员工目录、项目文件、`AGENTS.md` 和手动放入的资料原位保留。当前任务的“只读”约束覆盖终端、编辑器及有写效果的 MCP。
- **继续原来的组织关系。** 大嘴用 DeepSeek 也能派 GPT 员工；同项目可互相请教，子员工逐级汇报。已授权的日常工作直接做，不确定的先问管家，大嘴能代决的在授权内决定；需要你时只在大嘴原会话出现。保留你最多直接管到大嘴下一级员工的习惯。系统实名授权、飞书 OAuth 或 Windows 本人确认仍由相应身份完成。
- **你能看到的界面与回执。** 工作台继续统一管理员工、会话、工具、头像和组织图；飞书保留员工身份、私聊、已授权群和对应记录。状态关键词走现有快速查询；完成后撤下“思考中”。大嘴称呼「老板」或「您」，说清已经核实的结果，出错由自己说明。给老板的回复最多 1000 字，正好 1000 字直接发，超过就发简短摘要和完整 Markdown。文档任务交真实云文档链接。主动巡查沿用两小时，只提建议，批准后才做项目变更。
- **本机部署（11 月 26 日更新）。** 开机后由老板双击桌面 Dudu，网页和飞书一起启动。关闭本机管理窗口时可选择保留后台或同时停止服务。远程浏览器关页后，主机上的任务继续运行。公开仓库只放代码、测试夹具和说明。

## 三、需要重点复核的五处

| 问题 | 什么结果才算正确 | 对应工作包 |
|---|---|---|
| 配了独立会话目录，实际仍往个人 Codex 的索引写 | 员工连续两轮、重启一次后仍能接续，个人侧栏的会话 ID 集合无新增员工记录 | T2、T9 |

## 四、工单、会话和权限怎样配合

```text
飞书原消息 / 网页原消息
  → 大嘴找到业务任务，记录老板原话、引用、目标、本轮限制
  → 在该任务下派给指定员工，记录本次负责人和派工编号
  → 在员工项目根目录启动或恢复该任务的引擎会话
  → 员工查现状、做事、观察结果、必要时调整，再检查交付物
  → 员工把结果和证据交直属负责人，大嘴回到原消息下汇总
```

**四个编号各管一件事。** `WorkItem.id` 是长期任务号；`AgentJob.id` 是一次派工；`Thread.id` 是后台可查看的对话；原生会话 ID 由对应引擎签发。换员工或换供应商时，长期任务号不变，新的执行会话通过 `FeatureSession.previous_id` 找回交接记录。兼容的普通续办则复用原会话。不要拿某个模型的会话 ID 当整套系统的任务号。

**一次派工要保留的内容。** 复用工单的项目、经办人、依赖、验收和交付物。在现有派工事件中补齐老板原文/引用的可回查标识、明确指定的员工 ID、允许的资源和本轮只读等限制、负责人版本，以及模型实际选择。员工可以申请新步骤、调用已获准的工具。任务类型只帮助路由和说明结果；不能拿它替代授权判断。

**执行顺序**　T0 先给出实机基线；T1–T2 先打通一个本地员工；T3–T4 完成大嘴接续与纠错；T5–T6 解决其他模型、工具与审批；T7 接通二狗，T8 统一核对交付；T9 做对照、试运行和回退演练。各阶段先在隔离数据上完成。

## 七、你来验收：10 组真实使用场景

先用同一份合成小项目、同一模型/强度、相同工具和授权做桌面与员工对照。用两个内容相同的项目副本独立执行，避免第二个执行者捡到第一个的成果。桌面和员工都由验收人独立打开交付物或重跑约定命令；记录实际模型、项目快照、工具回执、产物和需要你介入的次数。耗时记实测值；不把单次网络延迟或模型文风当成功能差异。除轻量对照外，其余用例复用同一批任务，只在验证特定行为时增加一次派工。

| # | 你可以这样说 / 这样操作 | 怎样签字通过 |
|---|---|---|
| 1 | **“让 Jensen 修好验收项目里失败的测试，跑完告诉我。”** | 从指定根目录运行，能看到先失败再通过的真实结果；你独立重跑也通过。未要求你开员工会话、复制代码或运行命令。飞书和工作台指向同一任务。 |
| 2 | “用项目里配好的那个技能，读这张验收图，再用工具查一下编号。” | 技能取到项目专属标记，图片内容与样本吻合，MCP 返回预置的动态编号。员工能自主发现工具；每一项都能在记录里找到证据。 |
| 3 | **同时留两项工作；引用较早的回复说“按刚才那个要求继续”。** 再关闭网页、重启后台，继续一次。 | 命中被引用的任务、同员工及兼容的原生会话；另一项无新执行。私有会话编号稳定，个人 Codex 列表无员工新会话。无引用且两项均合理时，大嘴只问一次。 |
| 4 | 在旧版任务下说“接着做，按上一版要求”。 | 原工单号、老板原话、既有产物、历史记录都在；旧版没有原生 ID 的仅交接一次，之后能从新的后台原生会话恢复。 |
| 5 | “这单给错人了，交给二狗。已经做的别做第二遍。” | 原负责人停止，二狗看到已验证的进度；老消息仍能查到原任务，只有新负责人可交付；旧员工迟到的结果不会发给你当本轮结论。 |
| 6 | 大嘴用 DeepSeek，Jensen 用 GPT，再给一名员工单独选第二厂商，从飞书交代一次简短项目任务。随后切换该员工模型并续办。 | 三方真实请求和回执可区分，其他员工配置不变；续办任务号不变，跨厂商记录有交接。UI 展示实际供应商、模型和可用强度。 |
| 7 | “二狗读一下 Jensen 的验收产物，整理到你自己的目录。只读他的原件。”再触发一项需老板批准的操作。 | 二狗能读获准文件、写自己的目录，不能改 Jensen 文件；未获准员工读不到。普通操作继续，需你决定的仅在大嘴原会话出现一次，批准后接原任务。 |
| 8 | **“让二狗把我和指定联系人的聊天整理成飞书文档，放到指定文件夹。”** 引用回复说“分类收一收，原来的继续用”。 | 读全部获准的可见历史，实际经办和写入身份为二狗；目标文件夹只有预期文档。链接可开，正文按主题合并，可追溯原消息。重整同一份文档，不能只复述聊天条数。 |
| 9 | 在验收文件夹删除或移动测试文档，再说“检查一下刚才那份，继续整理”；另模拟写入成功后丢回执。 | 能区分删除、移动/无权、网络未知。确需重建时只建一份；未确认时先查。读回支持实际结论。缺权限由大嘴说明卡在哪一步；不会让你粘贴聊天。 |
| 10 | 员工执行时私聊它“进度”；同一消息重投一次；只留一个故意失败的测试，再请大嘴汇报。 | 状态查询不耗模型、记录随真实任务变化。无重复派工/发文；大嘴在原消息下说明未通过项。1000 字以内直接回复，超过时给简短摘要和完整 Markdown，最终送达后撤掉“思考中”。 |

**签收规则**　三项一起看：日常交互是否仍只需找大嘴；员工产物和证据是否达到同条件桌面基准；所有要求的岗位权限、供应商及真实飞书动作是否已独立验证。哪一项没达到就标哪一项。上线记录注明试点员工、旧版本、回退方式和仍欠的验证，供老板决定是否扩大范围。

**现场结果填写格式**　场景号 · 员工/供应商/模型 · 长期任务号 · 实际操作或产物链接 · 与桌面对照的差异 · 是否需要老板介入及原因 · 通过/失败/待授权/未测。比如第 1 组要附独立重跑的结果，第 8 组要附可打开的验收文档；只有一条“员工说已完成”不能签收。
