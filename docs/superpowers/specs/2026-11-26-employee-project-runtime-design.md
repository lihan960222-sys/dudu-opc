# 员工在自己的项目里工作 · 验收约定

**状态**　2026-11-26，提交老板审阅。这里约定产品行为，具体改动和验收口令见[执行计划](../plans/2026-11-26-employee-project-runtime.md)。

## 老板的一天

你在飞书对大嘴说“让 Jensen 把刚才那个问题修好，跑一下给我看”。大嘴能找到被引用的任务，把你的原话、相关决定和验收要求交给 Jensen。Jensen 在档案指定的项目根目录里读代码、修改、跑测试、检查结果。你关掉管理网页也能继续。最后，大嘴回到原消息下告诉你改了什么、验证了什么、哪里还卡着。你随时可以在后台或已绑定的员工私聊里查过程。

如果说的是“让二狗把和李晗讨论的内容整理到知识库”，做事的仍是二狗。它拿自己的飞书授权读资料、选做法、写文档、再打开核对。你说“原来的分类太多了”，它能接着改同一份文档。老板用自己的话下任务；每个任务同时保留可校验的工单编号、负责人、范围、验收条件和交付物。

## 哪些算达标

| 事项 | 验收口径 |
|---|---|
| 接口与运行地点 | 仍用原生 Suparagent、家中 Windows 主机、现有飞书网关和私网工作台。日常由大嘴派工并汇总，员工按汇报关系交结果。 |
| 项目工作能力 | 给桌面 Codex 和员工相同的项目快照、账号权益、模型、推理强度、工具和岗位授权，比较能否完成同一件事。员工能运行终端、Git、项目命令、测试，读取适用的项目指令、使用技能和 MCP，并核对产物。已有图片、文件等输入沿同一任务传递；岗位依赖的某个桌面工具无法在后台调用，就把该项列为差距。 |
| 谁决定怎么做 | 大嘴负责找人、保留原意、说清交付。员工自己查看现状，选择和调整步骤，验证后汇报。普通任务描述、模型猜的分类不能授予额外权限，也不能把员工已有的合适工具藏起来。老板明确说“只读”时，此轮执行只读。 |
| 独立会话 | 一个员工可以有多个任务。同任务、同员工、兼容的引擎配置续用同一原生会话。新任务独立。原生历史放在后台专用位置，员工任务仅从飞书和工作台访问；个人 Codex 项目列表不新增员工对话。 |
| 供应商和模型 | 每人独立选实际供应商、执行引擎、模型及所支持的推理强度。大嘴用 DeepSeek 可以指挥 GPT 员工；同一团队至少再实证一名员工本身能用另一厂商完成项目任务。切换时保留业务任务、证据和往来记录。兼容性差异和缺少的账号授权要显示在档案中。 |
| 权限 | 岗位最高档可在自己的目录读写修改。跨员工目录按岗位配置，允许时只读；飞书账号和资源单独授予。工具、终端子进程和后台连接都要遵守同一边界。员工有疑问先报直属负责人，由大嘴在老板已有授权内处理；需要老板决定的事项回到与大嘴的原对话。 |
| 接续与纠错 | 明确引用优先，明确点名锁定员工。有唯一上下文就续办，有歧义只问一次短问题。派错人员时保留原任务号，收回旧执行权，核对已做的事，再交新员工。换人、换引擎和重启都不能重复发文档或宣布错误的结果。 |
| 大嘴的交付 | 主消息礼貌、口语化、最多 200 字；细节多时附 Markdown。员工报告已读、草稿、实写、核对通过或受阻等真实状态。老板可以直接询问员工进度；主动汇报仍归大嘴。 |

## 设计选择

- **建议采用**“后台原生会话 + 员工专属项目目录 + 现有管家调度”。Codex 岗位沿用已有 App Server 适配器；其他供应商通过实测可用的引擎完成相同任务。服务可以按轮启动进程，持久性看会话能否恢复。旧项目的 Worker / Router 分工只作思路参考。[旧项目说明](https://github.com/lihan960222-sys/codex-super-agent#工作方式) · [Codex App Server 协议](https://developers.openai.com/codex/app-server/)
- 评估过两条较短的路。仅给当前临时会话打开终端，仍会丢失原生续接，并且会改变跨目录权限；直接使用个人 Codex 的历史目录，容易让员工对话出现在你的侧栏。两者都达不到上表的验收条件。
- **建议优先用目前已有的 DeepSeek 配置验证第二厂商的员工岗位**。实际模型从当前账号读取；假如其执行接口达不到岗位要求，如实列缺项，其他可用厂商分开验收。不默认购买服务，不静默切换计费账号。
- 工作目录、员工身份或模型发生重大变化时，由后台建立新的执行会话并做一次交接。旧工单及原始记录可查。只有需要改变原任务授权或处理冲突时才请老板选择。
- 先在同一主机的临时项目和验收文件夹演练，再让 Jensen、二狗分批切换；正式项目的既有文件、员工机器人、联系人绑定和个人 Codex 历史都属于要保护的数据。计划获批后才安排实施与现场验收。

## 建议你签收的三个默认选择

1. **同项目共用真实文件。** 两个任务各自保留会话，在同一目录按顺序修改，后一个任务能看见上次留下的文件。若你明确要做两个相互独立的方案，才另给工作副本。新接手的人按自己的权限取资料；原员工有权看的私聊正文、附件或内部摘要，不能随交接扩大可见范围。
2. **跨厂商按岗位的实际效果验收。** Codex 岗位要求原生会话真实恢复；其他厂商若通过兼容引擎持久保存完整的交互和工具结果，也可以参加同题验收，管理页标出实际执行方式。只会发起文字对话、或换模型就丢任务进度的组合，不作为可工作的开发岗位上线。
3. **已执行但没收到回执，先查再动。** 文档、消息等外部写入尽量经能记录操作、查回结果的工具。如果第三方接口无法确定上次是否生效，保留“待核对”，让大嘴说明到底哪一步不确定。普通终端和 MCP 可以照常处理获准工作，不自行重试有重复副作用的操作。
